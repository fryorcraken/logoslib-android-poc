# Cross-track critique

> Completeness critic run over all research tracks, 2026-09-25. It lists contradictions
> between tracks, spot-checks that settled them, gaps, and follow-up experiments.


### Overall
How well the six questions are covered:

(1) Module and dependency graph: answered and verified. lez_core declares dependencies [] and wraps only libwallet_ffi (the Rust LEZ light wallet). It reads chain state only from an LEZ sequencer over JSON-RPC. The framing "lez_core uses blockchain module" is wrong at the module level; the most likely source is joint packaging in blockchain-modules-release. The L1 (Bedrock) sits behind the sequencer (data availability, ordering, finality, bridge) and appears in wallet_ffi only as a build-time crate link. The RLN/delivery chain from the Electron POC is irrelevant: lez_rln 3.x and later link wallet_ffi directly.

(2) Circuits: answered from source, not compile-tested. "Blockchain circuits" means the Bedrock circom witness libs plus rapidsnark and GMP. They are pulled in through a single BasicAuthCredentials conversion in lez/common, which I confirmed as the only logos_blockchain reference there. They are never used at runtime, and no Android bundle exists. Patching them out beats building them with the NDK. The RISC Zero guest ELFs are prebuilt, and proving happens only behind wallet-ffi's `prove` default, which a public-only demo should drop.

(3) Upstream Android support: answered. There is none in liblogos, logos-module-builder or LEZ. logos-nix has an arm64-only Android Qt 6.11.1 set with no QtRemoteObjects, never built in CI. Official Qt 6.11.1 prebuilts for both ABIs are the practical route.

(4) Call route: half answered. Calling from the host is settled by experiment: the lp_* C ABI works from inside the liblogos_core process with no daemon and no LogosAPI C++. The only Qt C++ needed is a QCoreApplication created, started and exec'd on one dedicated thread. Module-to-module calls through generated wrappers plus capability_module were verified on desktop (lez_probe to lez_core). Where modules run on Android is NOT settled, and the tracks talk past each other. The only existing container spawns one JVM-less logos_host_qt per module. That needs minSdk 33 or higher (backtrace and CLOEXEC_DEFAULT), useLegacyPackaging, and LOGOS_HOST_PATH set to nativeLibraryDir. It also breaks HTTPS inside wallet_ffi, because rustls-platform-verifier needs a JavaVM, a cross-track problem no track spotted. In-process hosting would need a new container, reimplementing logos_host's module_initializer, relinking the plugins against a shared protocol library, and a build-time swap: registerLoader cannot override the default (confirmed in source). Spot-checks of Qt 6.11.1 suggest QCoreApplication tolerates having no JVM. Experiments X1 and X2 decide this cheaply and should run first.

(5) Packaging: well covered from docs, untested. Rebuild everything with NDK r27c and libc++_shared. Use lib*.so naming for anything in jniLibs. Ship .lgx files as assets and extract them to filesDir; plugins can be dlopen'd from there. On Android, lgx variant resolution gives linux-x86_64(-dev) (confirmed). Set TMPDIR short and explicit because of the 108-byte sun_path limit.

(6) Implementation plan: missing; no track produced one. Recommended order:
- M0: desktop checks X7 and X3.
- M1: Qt/QtRO smoke test on the x86_64 AVD (X1, X2). This is the gate between subprocess and in-process hosting.
- M2: cross-build the liblogos closure for x86_64-android API 34 on official Qt 6.11.1: Boost, OpenSSL 3, spdlog/fmt, libsodium, zlib, liblgx (ICU or the X8 port), package_manager_lib, logos-protocol, plugin-qt, qt-sdk, cpp-sdk, container-subprocess, module-loader-qt/logos_host_qt, liblogos_core, capability_module.
- M3: Kotlin app plus JNI shim (Qt-thread bootstrap, lp_* calls, delete[] handling); load capability_module and one trivial test module.
- M4: two small probe modules to show inter-module calls over liblogos's own QtRO transport before any Rust is involved.
- M5: wallet_ffi for Android (X3, X4: patched lez/common, no-prove, pcsc stub). Solve TLS with a local standalone http sequencer (X5) or a webpki-roots patch. Pin the lez_core rev per X6.
- M6: the demo. Offline base58 through lez_probe to lez_core, a wallet with calibration_limit set low, then a read of the block height. Writes only against a version-matched sequencer.

Biggest risks, in order:
1. JVM-less Qt in the child process.
2. TLS in wallet_ffi.
3. How much of the non-Qt native dependency tree has to be cross-built.
4. Whether wallet-ffi compiles for Android.
5. The first-call race and single-threaded blocking in lez_core.

### Contradictions
- [SETTLED BY SPOT-CHECK] Can a frontend add its own loader? android-pkg C19 and mobile-search C6 say yes: register it with ModuleManager::loaders().registerLoader() before logos_core_start. They are repeating upstream docs (module_manager.h:17-22, docs/spec.md:321). liblogos-arch C3 and its verifier_missed say the added loader can never be chosen. The source backs liblogos-arch. In /home/fryorcraken/src/logos-co/logos-liblogos/src/logos_core/module_manager.cpp:306-316, loaderRegistry() registers the default CompositeModuleLoader inside std::call_once the first time the registry is touched, so it is always first. In module_loader_registry.cpp:27-30, select() returns the first loader whose canHandle() is true. The only other way to pick a loader is loaderConfig['id'] (lines 16-24), and liblogos never fills that in. So an in-process loader works only via a build-time container swap or clearForTests()+registerLoader(); the headers for the latter are not installed.
- [OPEN, DECISION-CRITICAL] The tracks disagree on where modules should run on Android. android-pkg C23 recommends an in-process ModuleContainer and calls one subprocess per module a poor choice. call-routes C8/C9 (and its verifier_missed), rln-intermodule C15/C16 and desktop-probe C10/C12 all validated the opposite model: modules stay in logos_host_qt children, and only the calling host lives in the liblogos_core process and talks to them via lp_* over QtRO. The word 'in-process' is overloaded: call-routes means the caller is in-process, android-pkg means the modules are. liblogos-arch verifier_missed shows how much work in-process modules would take:
- a new container plus a new format loader (CompositeModuleLoader::load returns false when there is no host path, composite_module_loader.cpp:25-27);
- reimplementing module_initializer, which is compiled only into the logos_host_qt executable;
- relinking every plugin against the shared liblogos_protocol/qt_host (liblogos src/CMakeLists.txt:225-228 and 252-255: static copies caused 'every cross-module call was refused');
- recreating the capability_module host-services grant.
No track weighed this cost against the subprocess risks (a JVM-less child, phantom processes, useLegacyPackaging).
- [NEW, SETTLED BY SPOT-CHECK] lez-graph C22 and its verifier_missed propose adding a JNI init export to wallet_ffi so rustls-platform-verifier can check TLS certificates. That assumes wallet_ffi runs in a process with a JavaVM. Under the only existing container (liblogos-arch C1, desktop-probe C12), lez_core and its libwallet_ffi.so run inside a posix_spawn'd logos_host_qt child with no JVM (qt-android C19, android-pkg C23). The code rules this out:
- Every Android init path in rustls-platform-verifier takes a JNIEnv or JavaVM (/nix/store/a43h4q08b8vjj4x0m27bidn6p9y5a43w-cargo-package-rustls-platform-verifier-0.5.3/src/android.rs:94,110,120,152).
- global() panics with 'Expect rustls-platform-verifier to be initialized' when it was never initialized (android.rs:84-87).
- jsonrpsee uses it for https by default (/nix/store/vx2xv2jwb38a1knzrca2n5yqxmrkp91h-cargo-package-jsonrpsee-http-client-0.26.0/src/transport.rs:257-260).
- The LEZ lock pulls in rustls-platform-verifier 0.5.3 plus the -android crate (/home/fryorcraken/src/logos-blockchain/logos-execution-zone/Cargo.lock:5097,5149,10795-10819).
With subprocess hosting, HTTPS to https://testnet.lez.logos.co therefore needs one of: a LEZ patch using jsonrpsee with_custom_cert_store (client.rs:189) with bundled webpki roots; a plain-http sequencer; or in-process hosting of lez_core. No track connected these two findings.
- [SETTLED] Minimum Android API. qt-android C21, mobile-search C20 and android-pkg C14 treat API 28 as enough (Qt 6.11 / logos-nix floor). Two findings force API 33 or higher for the unmodified subprocess container:
- Build time: logos_host.cpp calls ::backtrace() (/home/fryorcraken/src/logos-co/logos-module-loader-qt/src/host/logos_host.cpp:30,148), and NDK r27c declares it __INTRODUCED_IN(33) (sysroot usr/include/execinfo.h:52).
- Run time: posix_spawnattr_setflags(POSIX_SPAWN_CLOEXEC_DEFAULT) returns EINVAL below API 33 (android-pkg verifier on C19, subprocess_container.cpp:532-537).
The API 34 AVD meets the requirement. minSdk 33 or higher also unlocks the NDK's ICU C API (API 31+), which matters for liblgx (see gaps).
- [SETTLED BY SPOT-CHECK] Where does the rapidsnark build download from? circuits C14 says the rev LEZ pins (logos-blockchain fork e91187f8, feat/nixify) honours RAPIDSNARK_LIB_DIR and maps Android targets to iden3 prebuilts. android-pkg verifier_missed says build.rs downloads from rapidsnark.zkmopro.org. They read different revisions. The local checkout /home/fryorcraken/src/logos-blockchain/logos-blockchain-rust-rapidsnark is zkmopro upstream (HEAD df3831a, 2025-08-19), and its crates/build.rs:8-73 has no RAPIDSNARK_LIB_DIR handling. So android-pkg describes a revision LEZ does not use. The point is moot if the Bedrock edge is patched out of lez/common.
- [SETTLED BY SPOT-CHECK] What variant name will liblgx report on Android? mobile-search's open question and desktop-probe C21 say unknown, possibly 'unknown'. liblogos-arch C13 says linux-arm64. The lgx source settles it: /nix/store/7f6d5ba9jv4hkn2r923kxjxac271i5hn-source/src/core/platform_variant.cpp:51-76 has only __APPLE__, __linux__ and _WIN32 branches, with no __ANDROID__ branch. Bionic defines __linux__, so an NDK build reports 'linux-x86_64' on the emulator and 'linux-arm64' on devices. 'unknown' only occurs on a target that matches no rule. The package manager also appends '-dev' unless LGPM_PORTABLE_BUILD is set. One caveat remains: it is still unproven that this store copy is the exact liblgx revision locked by logos-package-manager d88abaa.
- [SETTLED BY SPOT-CHECK] Does the wallet refuse a build whose program IDs differ from the sequencer's? The circuits verifier_missed says it does, citing lez/wallet/src/cli/mod.rs:243-264, and concludes an Android build must pin the matching LEZ rev 'even for public-only transfers'. Those asserts live only in the CLI's Command::CheckHealth arm (/home/fryorcraken/src/logos-blockchain/logos-execution-zone/lez/wallet/src/cli/mod.rs:238-275), not in WalletCore or wallet_ffi. desktop-probe C5-C8 shows lez_core 0.4.2 (LEZ v0.2.5-rc2 line, per rln-intermodule verifier_missed) running create_new, open and get_current_block_height against the testnet, even though lez-graph C16 says the testnet runs the v0.2.4 line. So a version match is needed for writes, whose transactions name program IDs (lez-graph C16, inferred). It is not needed to open a wallet or to read.
- [SETTLED BY SPOT-CHECK] Can the Kotlin host discover method names at runtime? call-routes C11(3) and its verifier_missed say no: lp_get_methods returns '[]' because remote introspection is not implemented (remote_transport.cpp:445-450). desktop-probe C4 got a 40-method list from `logoscore module-info`. Both hold. module-info does not use getMethods; it calls moduleClient->invokeRemoteMethod(name, "getPluginMethods") and "getPluginEvents" (/home/fryorcraken/src/logos-co/logos-logoscore-cli/src/core_service/core_service_impl.cpp:426-436). An Android host can very likely get the list the same way with lp_invoke(target, "getPluginMethods", "[]"); that exact lp_* call has not been run.
- [PARTLY SETTLED] Who sets TMPDIR on Android, and where do sockets land without it? qt-android C15 and liblogos-arch C6 say that without TMPDIR the QtRO sockets land in /tmp and listen fails. The liblogos-arch verifier on C6 says Android 13+ sets TMPDIR=cacheDir in every app process (ActivityThread). desktop-probe C26 cites QTBUG-98502, which says the files dir, and the call-routes verifier says Qt falls back to nativeTempPath(). On the API 34 AVD, TMPDIR is probably set already; the only unverified piece is the framework commit. Everyone agrees on what matters: set TMPDIR explicitly and keep it short. The sun_path budget matches across tracks. With an 82-char TMPDIR the path is 118 bytes and capability_module segfaults (call-routes verifier). desktop-probe C13 saw a 108-byte path fail and a 104-byte path work.
- [SETTLED] Event-loop and thread rules. rln-intermodule C16 says the thread that calls logos_core_start must pump the loop. Its verifier says that only applies when calls come from another thread. The liblogos-arch verifier on C5 says the owner thread is the QCoreApplication's thread, and that calling start from any other thread blocks or deadlocks. The Electron POC said a dedicated Qt thread 'does NOT work'. call-routes C8/C9/C16 verified by experiment the rule that satisfies all of these: construct QCoreApplication, call logos_core_start and run exec() on ONE dedicated thread, then load and call from other threads.
- [SETTLED] Must the Bedrock circuits be built for Android? The circuits summary and mobile-search C11 say an Android wallet_ffi needs Android-built circuit libs (NDK-built or stubs). The circuits verifier_missed and lez-graph verifier_missed say the only LEZ-to-logos-blockchain edge is one BasicAuthCredentials conversion, so a small patch removes the entire circuits/rapidsnark/GMP tree. Spot-check: in lez/common, logos_blockchain appears only at src/config.rs:5 and Cargo.toml:27 (/home/fryorcraken/src/logos-blockchain/logos-execution-zone/lez/common). One observation is still unexplained: circuits C11 found poc_generate_witness and 182 GMP symbols linked into the shipped .so. The likely cause is static initialisers keeping whole sections alive rather than real Rust reachability (inferred). The patch has not been compile-tested.
- [SETTLED BY VERIFIERS] Qt pins and 16 KB alignment.
- qt-android C3 says Qt 6.11.1 is used for iOS/Android at the rev liblogos pins. Its verifier shows that at f55bf91 the second Qt pin was Windows-only.
- android-pkg C14 says logos-nix's Android Qt is 'probably 4 KB aligned'. Its verifier says the android_16kb_pages feature turns on by itself, and qt-android C8 measured 16 KB on the official prebuilt.
- qt-android C4 names libQt6RemoteObjects as the only importer of Qt private API; its verifier found that libQt6Network imports private API too.
None of this matters for the x86_64 AVD (4 KB pages). It matters for arm64 devices and Play.
- [SETTLED BY VERIFIERS] What save() and restore_storage do. lez-graph C4 groups save() with the local-only methods. Its verifier shows save() runs client_rotation, which sends getLastBlockId over the network, and returns STORAGE_ERROR if that fails. It also shows restore_storage runs a full chain sync. desktop-probe C6 measured save at 1.0 s. lez-graph C5 ('open needs a reachable sequencer') is only true for a sequencer URL not yet in statistics.json.
- [STALE LOCAL CLONES] Several tracks analysed clones that are behind upstream while the experiments ran newer builds:
- lez-graph C3 lists the local 0.4.0 API (b220144). desktop-probe C4 and lez-graph C15 show the built 0.4.2 (825d2a4) lacks pinata/register/vault and adds payer arguments.
- rln-intermodule C6 says delivery master declares deps []. The upstream master is 0.3.0 with optional_dependencies (rln-intermodule verifier).
- liblogos-arch analysed local 7fee75b, while desktop-probe built db45024.
The port must pin the revs actually built and run in desktop-probe (liblogos db45024, logoscore 6a0a2f4, lez_core 825d2a4 or acf0cd50), not the local HEADs.
- [TASK FRAMING vs TRACKS] The orchestrator prompt calls the Electron POC 'months old'. liblogos-arch C21 and the rln-intermodule verifier date its commits to 2026-09-17/18 and find its description of upstream mostly accurate. One claim no longer holds. Its README table says calling a module in-process needs LogosAPI/LogosAPIClient C++ (README.md:221). call-routes C8 shows by experiment that the Qt-free lp_* C ABI calls modules from the liblogos_core process, with Qt C++ needed only to create and pump the QCoreApplication.

### Gaps
- Nothing has been run on Android or the emulator. Every Android behaviour below is inferred from source or docs: Qt Core bootstrap in a Kotlin app, a JVM-less logos_host_qt child, SELinux rules for QtRO local sockets, exec from nativeLibraryDir, dlopen of plugins from filesDir, Boost.Process on bionic.
- The decision-critical unknown is whether QtCore, QtRemoteObjects and QPluginLoader run in a JVM-less child spawned from an app. Spot-checks (inferred, untested) lower the risk:
- QCoreApplication init on Android calls appVersion() (qtbase 6.11.1 qcoreapplication.cpp:819-820). That builds QJniObject(context()), but context() returns nullptr without touching JNI (qjnihelpers.cpp:390-399), and QJniObject(jobject) returns early on null (qjniobject.cpp:802-806). The source copy is under /home/fryorcraken/src/fryorcraken/logoslib-android-poc/.work/verify-android-pkg/qtsrc.
- No Logos runtime source uses QStandardPaths, QSysInfo, QTimeZone or QNetworkInformation (grep over logos-protocol, module-loader-qt, plugin-qt, qt-sdk, liblogos, capability-module, logos-module and the lez module returned nothing).
The residual risk is any Qt path that reaches QJniEnvironment::getJniEnv, which dereferences a null javaVM (qjnienvironment.cpp:65-70). One example is QStandardPaths' external-storage paths, which call Environment statics without guarding on a context (qstandardpaths_android.cpp:49,72).
- TLS under the subprocess model is unaddressed. wallet_ffi runs in a JVM-less child, so rustls-platform-verifier cannot be initialised there (see contradictions). Three options have not been evaluated:
(a) patch LEZ MultiSequencerClient/SequencerClientBuilder to use jsonrpsee with_custom_cert_store with webpki roots;
(b) point the wallet at a plain-http sequencer. LEZ has a standalone sequencer that needs no Bedrock or indexer: /home/fryorcraken/src/logos-blockchain/logos-execution-zone/lez/sequencer/service/Cargo.toml:42-43, run as `cargo run --features standalone -p sequencer_service lez/sequencer/service/configs/debug` (README.md:218-222). The emulator can reach it at http://10.0.2.2:<port>. Its RPC port and bind address were not found in configs/debug/sequencer_config.json;
(c) host lez_core in-process.
- The emulator decides the ABI, and no track put the pieces together:
- android-pkg verifier_missed (sibling commit c3866c3): the arm64 AVD does not boot on this x86_64 host.
- mobile-search C1/C20, android-pkg C14: logos-nix Android Qt is arm64-only, has no QtRemoteObjects, and has never been built.
- qt-android: the official Qt 6.11.1 android_x86_64 prebuilt was not downloaded or measured.
Most wallet/circuits analysis targeted aarch64. The first milestone therefore has to be x86_64-linux-android on official Qt prebuilts; nobody said so.
- No attempt has been made to cross-build wallet-ffi for x86_64- or aarch64-linux-android, and the list of native blockers after patching lez/common and building with --no-default-features is unknown. Suspected blockers: pcsc-sys, ring, risc0 client crates, possibly openssl-sys. The size of a no-prove .so is not measured; the 59.8 MB recursion zkr should disappear (inferred). Whether risc0-zkvm without `prove` compiles for android is open (circuits, mobile-search).
- The non-Qt C/C++ dependencies of liblogos have no Android build plan or effort estimate:
- Boost 1.87: process, context, filesystem, date_time, atomic, system;
- spdlog, fmt, OpenSSL 3 (linked directly per qt-android verifier_missed), libsodium, zlib, nlohmann, ICU.
New finding: liblgx needs ICU only for /nix/store/7f6d5ba9jv4hkn2r923kxjxac271i5hn-source/src/core/path_normalizer.cpp, which uses the C++ icu::Normalizer2/UnicodeString API (lines 3-6, 15-47, 110), and CMakeLists.txt:44 has find_package(ICU REQUIRED). The NDK exposes the ICU C API unorm2_* from API 31 (android-ndk-r27c sysroot usr/include/unicode/unorm2.h:140). With minSdk 33 or higher, a small port to platform libicu could avoid cross-building ICU (about 37.7 MiB mapped on desktop, desktop-probe C16). Inferred and untried.
- No one has tried building module plugins for Android: capability_module, modules_state (optional), lez_core_plugin and a probe module. logos-module-builder has no Android support (mobile-search C9). Nobody has configured LogosModule.cmake with the NDK toolchain. The code generators have to run on the host (qt-android verifier_missed). Also unresolved: which SDK revs to pair with lez_core 825d2a4 or acf0cd50, and whether acf0cd50's vector<uint32_t> signatures fail under the current logos-cpp-sdk generator (lez-graph C20, inferred).
- The lez_core rev to target is undecided:
- 825d2a4 (0.4.2): built and run in desktop-probe; LEZ v0.2.5-rc2 with fees.
- acf0cd50 ('0.4.1-interim', v0.2.4): what lez-programs says matches the testnet.
- b220144: the local, stale 0.4.0.
Nobody has checked the testnet's program IDs against v0.2.4 or v0.2.5-rc2. This only matters for write transactions.
- How the child process resolves libraries is only inferred:
- DT_NEEDED for an executable exec'd from nativeLibraryDir: RUNPATH $ORIGIN or LD_LIBRARY_PATH;
- which linker namespace or config applies to /data/app executables when they dlopen plugins from filesDir;
- whether the child can reach the parent's QLocalServer socket in cacheDir (same UID and domain);
- whether seccomp allows setsid, prctl(PR_SET_PDEATHSIG) and pidfd_open from an untrusted_app child.
- logos-container-subprocess, logos-module-loader-qt (logos_host_qt) and Boost.Process v2 have never been compiled with the NDK. Unknowns: pidfd_open, the /proc/self/fd walk used for closefrom, and the GTest FetchContent that tests pull in unconditionally (liblogos-arch C11).
- The first-call token race has not been tested with the current protocol. lez-graph C19 and rln-intermodule C20 describe it: the first cross-module call can return a default value that looks like success. desktop-probe C10 reports that lez_probe calls succeeded but does not say whether the first call after a fresh load did.
- The Kotlin host's concurrency design is missing. lez_core handles calls one at a time: a 35 s create_new delayed the next call by 14.9 s (desktop-probe C6). lp_invoke's BlockingQueuedConnection has no timeout, so a busy Qt thread can wedge callers (call-routes C17). Nobody has specified per-call timeouts, a warm-up call, or which Kotlin threads call lp_*.
- App bootstrap order has not been specified or tested. It covers:
- Os.setenv for TMPDIR, LOGOS_HOST_PATH, QT_PLUGIN_PATH and LD_LIBRARY_PATH;
- System.loadLibrary order;
- whether Qt6Android.jar is needed at all. If Qt Core is loaded only as a DT_NEEDED dependency of the JNI shim, its JNI_OnLoad never runs (call-routes C18). The parent would then behave like the JVM-less child, which could remove the need for Qt6Android.jar; untested.
- where modules live. Options are .lgx files in assets extracted read-only to filesDir, or plugins renamed to lib*.so in nativeLibraryDir with symlinks, for which lgx_resolve_main behaviour is unknown.
- No track produced the concrete implementation plan (question 6), with milestones, a build-system choice (Nix vs plain NDK CMake/cargo), the demo sequence, or APK size. The pieces are scattered across call-routes, android-pkg, qt-android and desktop-probe.
- Offline wallet use and the demo's network use are not reconciled. On a first create_new, calibration is 100 sequential requests, each allowed up to jsonrpsee's 60 s timeout (lez-graph verifier on C5). A pre-seeded statistics.json or calibration_limit=3 avoids this (lez-graph C8, inferred), but it has not been tried with a sequencer that cannot be reached, as happens on an emulator with no route.

### Follow-up experiments
- X1. Does Qt run without a JVM? Cheapest decisive test. Write a script .work/scripts/critic-x1-qt-nojvm.sh that:
1. aqt-installs Qt 6.11.1 android_x86_64 qtbase and qtremoteobjects, plus linux_gcc_64 6.11.1 with qtremoteobjects, into .work/probe/qt;
2. builds two tiny executables with NDK r27c CMake (ANDROID_ABI=x86_64, ANDROID_PLATFORM=android-34, ANDROID_STL=c++_shared, QT_HOST_PATH=<gcc_64>). qro_server: QCoreApplication, QRemoteObjectHost('local:qro_t'), one enableRemoting'd QObject with a slot. qro_client: acquireDynamic, invoke the slot, print the result;
3. boots `emulator -avd delivery-demo -no-window`, adb-pushes the binaries plus libQt6{Core,Network,RemoteObjects}_x86_64.so and libc++_shared.so to /data/local/tmp/q, and runs server then client with TMPDIR=/data/local/tmp/q LD_LIBRARY_PATH=/data/local/tmp/q.
Pass means QCoreApplication, QtRO and QLocalServer work with no JavaVM, so the subprocess container is viable. A SIGSEGV in QJniEnvironment::getJniEnv means drop the subprocess route and build an in-process container.
- X2. Does it work from inside an app? Build a minimal Kotlin APK: minSdk 34, packaging.jniLibs.useLegacyPackaging=true, qro_server shipped as jniLibs/x86_64/libqro_server.so. Kotlin sets Os.setenv(TMPDIR, cacheDir), starts nativeLibraryDir/libqro_server.so with ProcessBuilder, and System.loadLibrary's a JNI lib that runs QCoreApplication plus the client on a dedicated thread. Build two variants: with Qt6Android.jar plus System.loadLibrary('Qt6Core_x86_64'), and with Qt Core loaded only as a DT_NEEDED dependency. Check `adb logcat | grep avc` and the client output. Pass settles exec from nativeLibraryDir, SELinux on the local socket, and whether Qt6Android.jar is needed.
- X3. Which native crates does wallet-ffi drag in on Android? No compile needed. In a scratch clone of logos-execution-zone at the LEZ rev pinned by the chosen lez_core, run `cargo tree -p wallet-ffi --no-default-features --target x86_64-linux-android -e normal,build --prefix none --offline`, then patch lez/common: drop logos-blockchain-common-http-client and the From<BasicAuth> impl at src/config.rs:5,51-55. Diff the -sys crates and the crates whose build scripts download things. If only pcsc-sys, ring and risc0 client crates remain and there is no lbc-build or rust-rapidsnark, the patch-out route is confirmed. If lbc crates remain, another dependency edge exists.
- X4. Does wallet-ffi actually compile for Android? Medium build, run after X3.
